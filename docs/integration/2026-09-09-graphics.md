## Final rendering ownership
The overlap audit was resolved into one clear production ownership model.

### #385 vs #390 visual catalogs
- `VisualCatalog` is the **single cross-domain presentation metadata layer** for #385/#390.
- It supplies bounded, validated, deterministic authored metadata and overrides.
- `ShipVisualCatalog` remains the authoritative authored ship geometry/silhouette/hardpoint source from #393.
- Rich celestial definitions remain owned by the #392 celestial catalog/renderer.
- `StationRenderer` remains the authoritative station-architecture renderer from #396.
- `SpaceBackgroundRenderer` remains the production system-background renderer from #391.
- The older competing `VisualDefinitionCatalog` / alternate `StationVisualCatalog` renderer families were not carried into the final integration.

This avoids duplicating complete geometry catalogs simply to satisfy #385. The generic cross-domain catalog augments the richer domain implementations rather than competing with them.

### #385 / #396 / #398 station rendering
- `StationRenderer` owns authored station silhouettes and architecture.
- `StationPresentation` owns contextual overlays/readability.
- Gameplay interaction radii remain the legacy authoritative bounds; larger authored visuals do not change collision/hit-test behavior.
- At strategic zoom below `0.55`, stations retain authored type-specific silhouettes while skipping sub-pixel moving gantries/trusses/windows. Full architecture returns above that LOD.
- #398 overlays remain separate rather than creating another station renderer.

### #393 / #394 / #401 / #403 ship rendering
- #393 owns hull geometry, silhouette identity and hardpoints.
- #394 owns material/panel/faction-accent presentation layered on that geometry.
- #401 provides bounded cached repository-backed art assets with safe fallbacks.
- #403 consumes production ship/hardpoint information for VFX; it does not own hull geometry.
- Medium LOD uses the bounded `ShipSpriteCache` and keeps authored silhouette/material/ownership variation while dropping unreadable micro-panel texture.
- Close LOD keeps repository-backed micro-panel art only when projected size makes it readable; per-hull panel overlays are rasterized/cached once in a bounded cache rather than rebuilt per ship per frame.

### #391 / #392 / #399 / #409 environment composition
- #391 owns deterministic layered system backgrounds/parallax.
- #392 owns stars, planets, moons, atmosphere/rings/surface treatment.
- #399 owns resource-node environments and material readability.
- #409 owns bounded ambient environmental life/motion.
- Cross-domain metadata can seed/override cosmetic presentation but does not replace these production renderers.

### #403 / #405 / #408 VFX lifecycle and performance
- Combat VFX and destruction effects remain production systems with bounded work.
- #408 validates sprite-cache limits/accounting, destruction particle/debris/vent/lifetime budgets, active-effect admission caps and representative stress scenes.
- Cosmetic systems do not write authoritative combat/economy/network state.

## Remaining risks / handoff notes
1. **Pre-existing network-validator compile mismatch:** `TcpConnectionIdentityValidator` at the frozen graphics baseline is out of sync with the proof-aware `PeerServerSide.resume(...)` API. It is intentionally not fixed here because that belongs to the security/network stream. Graphics CI isolates only that file in temporary Actions worktrees.
2. **Hosted timing variance:** GitHub-hosted runners can produce p95 scheduling/GC spikes. The integration gate therefore uses same-runner baseline-vs-head p50 for the 20% regression decision while retaining p95/max reports and deterministic structural budget checks.
3. **Future art growth:** the central generic catalog should remain presentation metadata, not evolve into a second copy of every rich domain catalog. New hull/station/celestial content should preserve the ownership boundaries documented above.
4. **LOD tuning:** strategic station silhouettes and ship panel-detail thresholds are intentionally readability/performance driven. New very large/small authored assets should be checked against #408 fixtures when introduced.
