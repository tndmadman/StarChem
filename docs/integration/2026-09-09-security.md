## Reconciliation performed
### Game-state authority — #395 + #397
- Retained `RespawnAuthority` as the server-owned ACTIVE → DEFEATED → RESPAWNING → ACTIVE lifecycle.
- Retained galaxy-wide live-asset checks; respawn eligibility cannot be created by a packet or by changing the viewed system.
- Retained server-selected home spawning and synchronized duplicate/concurrent respawn protection.
- Retained observer conversion identity derivation from the authenticated connection, live-asset rejection, invitation authorization, read-only observer behavior, and invitation-authorized visibility mode.
- PUBLIC observer snapshots remain detached from a live player's visibility identity, preventing FOW/player-perspective inheritance.
- The observer helper and respawn authority both rely on authoritative galaxy state. The observer helper redundantly iterates system IDs around the global asset query, but this was left intact because it is not a bypass and changing it would add unnecessary behavior drift.

### Pre-auth identity/resource abuse — #402 + #404
- Retained the real socket source address throughout JOIN/registration. Remote registration authorization is carried as a separate boolean policy input rather than expressed by substituting loopback.
- Real address remains available to auth attempt limiting, admission/moderation policy, audit logging, developer authorization, and peer state.
- Retained the 4,096-character / 32-field / 512-character-per-field bounded handshake parser.
- Retained the 16 KiB raw pre-auth TCP ceiling from the length header before payload allocation/UTF-8 decoding, while authenticated traffic keeps the independent 512,000-byte transport ceiling.
- Retained size-weighted JOIN/RESUME throttling and bounded unauthenticated connection/deadline controls.

### Session/TLS identity — #400 + #406
- Retained reference → fresh SESSION_CHALLENGE → HMAC proof resume. The challenge is connection/player bound, time bounded, consumed on proof attempt, and successful recovery rotates session material.
- Retained bounded previous-token proof recovery for a lost rotated WELCOME while preventing reuse after successful recovery/expiry.
- Retained explicit remote TLS first-use trust: an unseen remote certificate creates an unverified trust request and blocks normal login/session traffic until approved.
- Matching pins reconnect automatically; mismatch fails closed. Pin replacement is compare-and-replace against the expected current pin, so stale approval cannot overwrite a newer trust decision.
- Same-machine/loopback automatic TLS trust remains an intentional local-host exception.

## Integration-specific fix discovered
The first combined integration build exposed a stale validator call site: `TcpConnectionIdentityValidator` still called the removed seven-argument bearer-token resume API. Runtime #400 was correct, but the branch could not compile.

The validator was reconciled to exercise the real two-phase flow instead:
1. derive a non-secret session reference from the token digest;
2. prove that the reference alone does not bind the replacement connection;
3. receive a fresh `SESSION_CHALLENGE`;
4. produce the HMAC proof from the token digest + player + nonce;
5. bind only after valid proof;
6. continue its original stale-connection-ID regression.

The insecure bearer-only overload was **not** restored.

## Remaining security concerns
No assigned-issue bypass remains known from this reconciliation. Two design notes remain intentional rather than defects:
- loopback/same-machine TLS certificate changes are automatically trusted for local-host convenience; remote addresses do not receive this exception;
- Linux CI can fall back to StarChem's owner-only credential-file storage when OS credential storage is unavailable; the validators reported that fallback but did not fail.

The #400 suite explicitly exercises wrong-session challenge/proof binding. Cross-server reuse is additionally separated by each server's retained session/token state and by #406 endpoint TLS identity; no bearer-only network resume path remains.
